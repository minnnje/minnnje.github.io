Tied Weights와 meta device: 모델이 조용히 안 읽히는 경우

Subject MLOps / HuggingFace Ecosystem
2026. 8. 12 · 5분 읽기

오늘 배운 것

남이 만든 저장소를 재현하다가 이 에러를 만났다.

1

RuntimeError: Tensor on device cpu is not on the expected device meta!

from_pretrained()는 예외 없이 끝났고, 모델 객체도 멀쩡히 반환됐다. 그런데 임베딩 가중치 하나만 meta device에 남아 있었다. 추적해 보니 원인은 코드가 아니라 네 겹으로 쌓인 환경 요인이었다.

  1. facebook/opt-125m의 main 리비전에는 model.safetensors가 없다.
  2. 그래서 use_safetensors=True를 주면 transformers가 병합되지 않은 변환 PR(refs/pr/51)을 찾아가서 받아온다.
  3. 그 변환본은 tied weight를 embed_tokens.weight가 아니라 lm_head.weight라는 이름으로 저장했다.
  4. 그런데 transformers는 lm_head.weight를 “원본이 아니라 파생본"으로 취급한다. 그래서 무시하고, 원본을 찾다가 못 찾고, 조용히 meta로 남긴다.

핵심 교훈은 따로 있다. 에러가 났을 때 남의 코드부터 고치려 들면 안 된다. 저장소의 커밋 날짜와 내가 설치한 패키지의 릴리스 날짜를 대조하는 게 먼저다. 이번 경우 내가 깐 transformers 4.57.3은 저장소가 쓰이던 시점보다 5개월 오래된, 메이저 버전 하나 낮은 물건이었다.

핵심 개념 정리

1. Tied weights: 같은 텐서를 두 이름으로 부르는 것

많은 언어모델이 입력 임베딩과 출력 projection에 같은 가중치 행렬을 쓴다. embed_tokens는 토큰 ID를 벡터로 바꾸고(\(V \times d\)), lm_head는 벡터를 어휘 전체에 대한 점수로 되돌린다(\(d \times V\)). 둘은 전치 관계라 하나로 공유할 수 있고, OPT-125M 기준 이것만으로 파라미터 3,860만 개(모델 전체의 약 31%)를 아낀다.

HuggingFace에서는 이걸 두 가지로 표현한다.

  • config.tie_word_embeddings = True — 묶으라는 선언
  • model._tied_weights_keys = ['lm_head.weight'] — 어느 쪽이 파생본인지의 선언

두 번째가 이번 사건의 열쇠다. _tied_weights_keys에 들어간 이름은 “이건 체크포인트에서 읽지 말고, 원본에서 tie해서 만들어라"라는 뜻이다. 즉 transformers는 embed_tokens가 원본, lm_head가 사본이라고 전제한다.

실제로 확인해 보면 두 텐서는 저장소를 거치지 않고도 같은 메모리를 가리킨다.

1
2

m.model.decoder.embed_tokens.weight.data_ptr() == m.lm_head.weight.data_ptr()
# True

2. main에 safetensors가 없으면 transformers는 PR을 뒤진다

facebook/opt-125m의 main 리비전 파일 목록을 직접 조회하면 이렇다.

model.safetensors가 없다. 2022년에 올라온 모델이라 그렇다.

그러면 use_safetensors=True는 실패해야 할 것 같은데, 실패하지 않는다. transformers에는 safetensors_conversion.py라는 모듈이 있어서, safetensors가 없으면 변환 봇이 열어둔 PR을 찾아간다.

3. 그래서 무슨 일이 벌어지나

봇이 변환할 때 tied weight를 어느 이름으로 저장할지가 문제였다. 이 변환본에는 lm_head.weight만 들어 있고 embed_tokens.weight는 없다. 그런데 로더는 lm_head.weight를 파생본으로 보고 건너뛴다. 원본을 찾지만 없다. 결과적으로 아무것도 읽지 않은 채 초기화 시점의 meta 텐서가 그대로 남는다.

가장 고약한 부분은 에러가 안 난다는 것이다. from_pretrained()는 조용히 끝나고, 한참 뒤 그 텐서를 실제로 쓰는 순간에야 터진다.

1
2

hidden_states = token_embeds + position_embeds
# RuntimeError: Tensor on device cpu is not on the expected device meta!

token_embeds는 meta(연산 그래프만 있고 데이터가 없는 가짜 텐서), position_embeds는 cpu라서 더할 수 없다는 뜻이다. 스택 트레이스만 보면 모델 구현 코드가 잘못된 것처럼 보이지만, 실제 사고는 수십 줄 위 from_pretrained() 안에서 이미 끝나 있었다.

4. 진짜 원인은 버전이었다

같은 코드를 로딩 인자만 바꿔 돌려보면 범위가 좁혀진다.

인자embed_tokens.weight
torch_dtype=torch.float16cpu
torch_dtype="auto"cpu
use_safetensors=Truemeta
torch_dtype="auto", use_safetensors=Truemeta

use_safetensors=True가 유일한 방아쇠다. 기본값(None)은 “safetensors를 선호하되 없으면 .bin으로 폴백"이라 무사히 넘어간다.

여기서 코드를 고치고 싶어지는데, 그 전에 시점을 대조해야 한다. PyPI에서 릴리스 날짜를 직접 뽑아 보면 이렇다.

날짜
저장소에 use_safetensors=True가 커밋된 날2026-04-22
그날 나온 transformers5.6.0
저장소 마지막 커밋2026-05-24 (당시 최신 5.9.0)
내가 설치한 4.57.3의 릴리스2025-11-25

원 저자는 transformers 5.x를 쓰고 있었고, 나는 5개월 오래된 4.x를 깔아둔 것이었다. 실제로 5.9.0에서 같은 호출을 돌리면 정상 로드된다.

1
2

transformers: 5.9.0
embed_tokens -> cpu torch.float16

같은 체크포인트, 같은 코드, 다른 해석. 고쳐야 할 건 코드가 아니라 내 환경이었다.

pyproject.toml이 이걸 막아주지 못한 것도 짚어둘 만하다.

1

dependencies = ["torch>=2.0", "transformers>=4.30", "tqdm", "datasets"]

하한만 있고 상한이 없다. 4.57.3은 이 제약을 형식적으로 만족하지만 실제로는 동작하지 않는다. 하한만 있는 의존성 선언은 “이 버전에서 됩니다"가 아니라 “이 버전보다 낮으면 확실히 안 됩니다"까지만 보장한다.

헷갈렸던 부분

  • 처음엔 캐시가 깨진 줄 알았다. 스냅샷 디렉터리 두 개에 파일이 나뉘어 있었기 때문이다. 하지만 HF 캐시는 리비전 단위로 실제 받은 파일만 심볼릭 링크로 두기 때문에, 리비전이 둘이면 디렉터리도 둘인 게 정상이다. refs/main을 직접 읽어보고서야 나머지 하나가 PR ref라는 걸 알았다.
  • meta device를 “GPU 메모리 부족 때 생기는 것"쯤으로 오해하고 있었다. 실제로는 shape/dtype만 있고 저장 공간이 없는 텐서로, 모델 골격을 먼저 만들고 가중치를 나중에 채우는 방식(low_cpu_mem_usage)에서 정상적으로 쓰인다. 문제는 meta 자체가 아니라 채워지지 않고 남았다는 것이다.
  • 로딩 인자를 하나씩 바꿔가며 표를 만든 게 결정적이었다. 스택 트레이스가 가리키는 곳(models/opt.py의 덧셈)은 사고 현장이 아니라 증상이 드러난 곳이었다. 조용히 실패하는 버그는 “언제부터 잘못됐나"를 이분법으로 좁히는 게 스택 트레이스를 노려보는 것보다 빠르다.

확인 질문

_tied_weights_keys에 들어간 이름은 무슨 뜻인가?

“이 이름의 텐서는 체크포인트에서 읽지 말고, 원본에서 tie해서 만들어라"는 뜻이다. 즉 어느 쪽이 원본이고 어느 쪽이 파생본인지를 선언하는 것이다. OPT는 ['lm_head.weight']이므로 embed_tokens가 원본, lm_head가 파생본이다. 체크포인트가 반대 규약(원본을 lm_head.weight로 저장)으로 만들어져 있으면, 로더는 파생본을 무시하고 원본을 찾다가 못 찾는다.

use_safetensors=True와 기본값(None)은 뭐가 다른가?

기본값은 “safetensors가 있으면 쓰고, 없으면 .bin으로 폴백"이다. True는 “safetensors를 반드시 써라"라서 폴백 경로가 막힌다. 그리고 main에 safetensors가 없으면 transformers는 실패하는 대신 safetensors_conversion.py를 통해 열려 있는 변환 PR을 찾아간다. 즉 True는 단순히 포맷 선택이 아니라, 경우에 따라 다른 리비전에서 받아오게 만드는 스위치다. 재현성이 중요하면 revision=을 명시적으로 고정하는 게 안전하다.

이 에러를 만났을 때 코드를 고치는 게 왜 나쁜 선택이었나?

증상만 사라지고 원인은 남기 때문이다. use_safetensors=True를 지우면 그 모델은 로드되지만, 라이브러리 버전이 어긋나 있다는 사실은 그대로다. 그 어긋남은 다른 곳에서 다시 터진다. 게다가 재현을 목적으로 특정 태그를 체크아웃해둔 상태에서 소스를 수정하면, 원본과의 diff가 생겨 “내가 재현한 것"이 무엇인지 흐려진다. 순서는 ① 저장소 커밋 날짜 확인 → ② 설치된 패키지 릴리스 날짜 대조 → ③ 격리된 환경에서 가설 검증 → ④ 그래도 코드 문제면 그때 수정 제안이다.

왜 from_pretrained()가 그 자리에서 에러를 내지 않았나?

읽지 못한 키를 “누락"이 아니라 “tie로 채워질 것"으로 분류했기 때문이다. 파생본으로 선언된 키는 체크포인트에 없는 게 정상이므로 missing key 경고 대상이 아니다. 그래서 검증을 통과하고, 실제로 그 텐서를 연산에 쓰는 시점까지 문제가 드러나지 않는다. 로딩 직후 [n for n, p in model.named_parameters() if p.device.type == 'meta']로 직접 확인하는 습관이 도움이 된다.
